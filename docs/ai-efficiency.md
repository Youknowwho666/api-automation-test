# AI 辅助用例生成的实测记录

> 本文记录一次可复现的 AI 提效实验：让 AI 生成一批接口测试用例，再用**三层漏斗**逐条验收，
> 得出真实的**采纳率**与**变异杀伤率**。数据由 `ai_funnel.py` 与 `mutation_demo.py` 产出，
> 原始数据见 `docs/ai-efficiency.json`、`docs/mutation-report.json`。

## 为什么需要这套验收机制

AI 生成用例的速度远超人脑，但**不能直接入库**。实测下来，AI 输出的问题集中在三类：

| 问题类型 | 表现 | 危害 |
| --- | --- | --- |
| 幻觉 | 断言了接口根本不存在的字段/状态码 | 用例必挂，浪费时间 |
| 断言空转 | 只判 `status_code == 200` | 服务端返回错数据照样「通过」 |
| 语义误判 | 假设了多少并不成立的系统行为（如有状态持久化） | 用例本身就是错的 |

所以每一条 AI 候选用例都要过三道门。

## 三层漏斗定义

```
AI 生成的候选用例
        │
        ▼
┌───────────────────────┐
│ L1 可执行性            │  语法正确？接口存在？数据成立？跑一次看红不红
└───────────┬───────────┘
            ▼
┌───────────────────────┐
│ L2 断言有效性          │  有没有契约断言 + 业务值断言？只判 200 不算
└───────────┬───────────┘
            ▼
┌───────────────────────┐
│ L3 变异杀伤率          │  往实现里注入缺陷，这条用例能不能失败？
└───────────┬───────────┘
            ▼
        采纳入库
```

- **L1 可执行性**：把用例真跑一遍，能跑通才算数。这一步专门拦 AI 幻觉。
- **L2 断言有效性**：人工审断言。必须同时具备**契约断言**（字段完整性）和**业务值断言**（值是否正确），
  只断言状态码的一律打回。
- **L3 变异杀伤率**：不是"看起来写了断言"就算有效，而是注入真实缺陷后用例必须变红。
  这是最硬的一关。

## 实验结果

### 总体数据

| 指标 | 数值 |
| --- | --- |
| AI 生成候选用例 | **20 条** |
| L1 可执行 | 15 条（**75.0%**） |
| L2 断言有效 | 10 条（**50.0%**） |
| L3 变异杀死 | 10 条（**50.0%**） |
| 最终采纳 | **10 条** |
| 去重后净新增 | **9 条** |
| **采纳率（含重复）** | **50.0%** |
| **采纳率（净新增）** | **45.0%** |

> 一句话结论：**AI 一次生成的 20 条用例里，最终能直接入库的只有 10 条，净新增 9 条 —— 采纳率约 45%~50%。**
> 换句话说，AI 负责产出候选、把效率提上来，但**约一半的产出需要在人工验收环节被淘汰或改写**。

### 淘汰原因分布

| 原因 | 条数 | 占比 |
| --- | --- | --- |
| 断言有效性不足（只判状态码 / 断言维度单一） | 5 | 50% |
| 对被测系统的状态性做了错误假设 | 2 | 20% |
| AI 臆造接口契约（字段/状态码/响应结构不存在） | 3 | 30% |
| 合计淘汰 | **10** | 100% |

**淘汰的一半都是「断言不够硬」** —— 这恰好说明 L2 是漏斗里最关键的一层。
AI 很会写"能跑通"的用例，但不擅长判断"这条断言到底有没有价值"。

### L3 变异杀伤率（实测）

L3 不是估算，是真的往业务 API 层注入缺陷，看用例是否变红：

| 变异体 | 注入的缺陷 | 结果 | 抓住它的断言 |
| --- | --- | --- | --- |
| M1 | 筛选参数 `userId` 被静默忽略 | ✅ 失败 | 断言每条结果 `userId == 1` |
| M2 | 更新接口丢弃 `title` 字段 | ✅ 失败 | 断言更新后 `title` 为新值 |
| M3 | 分页参数 `_limit` 被丢弃 | ✅ 失败 | 断言返回条数 `== 5` |
| M4 | 详情接口固定返回 `id=1` | ✅ 失败 | 断言返回 `id` 等于请求 `id` |
| M5 | （基线对照，不改代码） | ✅ 通过 | 验证测试本身未损坏 |

**变异杀伤率 4/4 = 100%** —— 最终采纳的用例确实能抓住真实缺陷，不是"写了个样子"。

复现命令：

```bash
python docs/tools/mutation_demo.py     # 注入缺陷 → 跑用例 → 自动还原
```

## 方法论：怎么用 AI 才划算

实测下来，AI 在这件事上性价比最高和最差的场景泾渭分明：

**适合交给 AI 的：**
- 已有用例的**批量变体**（正常值改边界值、改空值、改超长）
- **样板代码**（新模块的 API 封装、Page Object 骨架）
- 从接口文档**提炼字段清单**，生成契约断言草稿

**不适合交给 AI 的：**
- 判断"这条断言有没有业务价值"—— 必须人来定
- 涉及被测系统**状态性/时序**的用例 —— AI 容易想当然
- 异常路径的**预期状态码** —— AI 经常照搬常规语义，实际接口未必那么设计

**工作流建议：** AI 生成 → 跑一遍（L1）→ 人工审断言（L2）→ 变异测试抽查（L3）→ 入库。
把 L1 自动化，L2 靠人，L3 抽查，整体效率提升明显，同时守住质量底线。
